# Requirements Document

## Introduction

This document defines the requirements for the Infrastructure Storage & Queue feature of the ALSAQI audit management system. The feature introduces MinIO S3-compatible object storage to replace filesystem-based file storage, Redis + BullMQ for background task processing of heavy operations (file uploads, PDF generation, notifications), and TLS/SSL certificate management for encrypted inter-service communication. These requirements are derived from the approved design document and ensure the system can scale horizontally, process files asynchronously without request timeouts, and secure all internal traffic.

## Glossary

- **StorageService**: The service component that abstracts all MinIO S3-compatible object storage operations behind a domain-oriented API
- **QueueService**: The service component that manages BullMQ job queues for background processing, encapsulating Redis connection and job lifecycle
- **WorkerManager**: The component that orchestrates BullMQ workers, registering processor functions and managing worker lifecycle
- **CertificateManager**: The component that centralizes TLS certificate loading and rotation for all inter-service connections
- **FileRecord**: The database entity tracking metadata for uploaded files including storage key, bucket, checksum, and status
- **JobRecord**: The database entity tracking background job status, progress, and results in PostgreSQL
- **Presigned_URL**: A time-limited, scoped URL generated by MinIO that grants temporary access to a specific storage object
- **BucketName**: One of the defined storage buckets: evidence, reports, temp, or backups
- **JobType**: One of the registered background job types: process-file, generate-pdf, send-notification, or cleanup-temp

## Requirements

### Requirement 1: File Upload to Object Storage

**User Story:** As an auditor, I want to upload files (evidence, documents) so that they are stored reliably in object storage without blocking my workflow.

#### Acceptance Criteria

1. WHEN a user uploads a file, THE StorageService SHALL validate the file's content-detected MIME type against the allowed list (application/pdf, application/msword, application/vnd.openxmlformats-officedocument.wordprocessingml.document, application/vnd.ms-excel, application/vnd.openxmlformats-officedocument.spreadsheetml.sheet, image/png, image/jpeg, image/gif) and reject disallowed types with an error message indicating the detected type and the list of accepted types
2. WHEN a user uploads a file, THE StorageService SHALL validate the file size is greater than 0 bytes and does not exceed the per-bucket maximum (evidence: 50MB, reports: 100MB) and reject files outside these bounds with an error message indicating the actual size and the allowed maximum
3. WHEN a user uploads a file, THE StorageService SHALL validate that the filename does not exceed 255 characters and contains no path traversal sequences (../, ..\, //, or null bytes), rejecting invalid filenames with an error message indicating the validation failure reason
4. WHEN a valid file is uploaded, THE StorageService SHALL stream the file to the MinIO temp bucket without buffering the entire file in API memory
5. WHEN a file is stored in the temp bucket, THE StorageService SHALL compute a SHA-256 checksum of the file content and store the resulting 64-character hex string in the FileRecord for integrity verification, regardless of whether the file passed or failed earlier MIME type or size validation
6. WHEN a file is accepted for upload, THE API SHALL return HTTP 202 Accepted with a job ID for status polling rather than waiting for processing to complete
7. WHEN a file upload completes to the temp bucket, THE StorageService SHALL create a FileRecord in PostgreSQL with status set to "uploading", the original sanitized filename, storage key, bucket name, content type, size in bytes, checksum, and uploading user ID
8. IF MinIO is unreachable or returns a connection error during file upload, THEN THE API SHALL return HTTP 503 Service Unavailable with an error message indicating that storage is temporarily unavailable and the upload should be retried

### Requirement 2: Background File Processing

**User Story:** As a system operator, I want file processing to happen asynchronously in background workers so that API response times remain fast and the system can scale.

#### Acceptance Criteria

1. WHEN a file is uploaded to the temp bucket, THE QueueService SHALL enqueue a process-file job with the temp key, target bucket, and file metadata including fileId, storageKey, checksum, and contentType
2. WHEN a process-file job is picked up by a worker, THE WorkerManager SHALL set the FileRecord status to "processing" and copy the file from the temp bucket to the permanent target bucket
3. WHEN a file is copied to the permanent bucket, THE WorkerManager SHALL verify the SHA-256 checksum matches the original upload checksum
4. IF the checksum verification fails after copy, THEN THE WorkerManager SHALL delete the corrupted file from the permanent bucket, mark the job as failed, set the FileRecord status to "failed", and retain the temp file for investigation
5. WHEN a file is successfully processed, THE WorkerManager SHALL delete the temp file and update the FileRecord status to "ready"
6. WHEN a process-file job fails, THE QueueService SHALL retry up to 3 times with exponential backoff starting at 2000 milliseconds before marking the job as permanently failed
7. WHEN a job completes or fails, THE QueueService SHALL update the corresponding JobRecord in PostgreSQL within 5 seconds
8. IF the temp file does not exist when a worker picks up a process-file job, THEN THE WorkerManager SHALL mark the job as failed with an indication that the source file was not found and SHALL NOT retry the job

### Requirement 3: File Download via Presigned URLs

**User Story:** As an auditor, I want to download files securely through time-limited URLs so that file access is controlled and auditable.

#### Acceptance Criteria

1. WHEN an authenticated user requests a file download, THE StorageService SHALL generate a Presigned_URL scoped to the specific object key with an expiry duration defaulting to 3600 seconds, configurable between 60 and 86400 seconds; IF a requested duration falls outside this range, THEN the system SHALL clamp it to the nearest valid boundary
2. WHEN a Presigned_URL is generated, THE API SHALL redirect the user to the Presigned_URL via HTTP 302
3. IF a user attempts to access a Presigned_URL after its expiry duration has elapsed or IF the expiry status cannot be definitively determined as valid, THEN THE StorageService SHALL deny access and return an HTTP 403 response
4. THE StorageService SHALL generate Presigned_URLs only for FileRecords with status ready
5. IF a user requests download of a file that does not exist or has a non-ready status, THEN THE API SHALL return HTTP 404 with an error message indicating the file is not available for download
6. IF a user requests download of a file they are not authorized to access, THEN THE API SHALL return HTTP 403 with an error message indicating insufficient permissions

### Requirement 4: PDF Report Generation

**User Story:** As an auditor, I want to generate PDF reports from audit data so that I can share findings in a professional format without waiting for generation to complete.

#### Acceptance Criteria

1. WHEN a user requests PDF report generation, THE QueueService SHALL enqueue a generate-pdf job with the report ID, audit ID, and template name
2. WHEN a generate-pdf job is requested, THE API SHALL return HTTP 202 Accepted with a job ID for status polling
3. WHEN a generate-pdf worker processes a job, THE WorkerManager SHALL fetch the full audit data (findings, recommendations, and evidence) from PostgreSQL
4. IF the audit data language is Arabic, THEN THE WorkerManager SHALL render the PDF with RTL text direction
5. WHEN a PDF is generated, THE WorkerManager SHALL upload the PDF to the reports bucket at path audits/{auditId}/reports/{reportId}.pdf with content type application/pdf
6. WHEN a PDF is successfully generated and stored, THE WorkerManager SHALL update the report record in PostgreSQL with status ready, storage key, and file size in bytes; THE WorkerManager SHALL NOT set status to ready unless both PDF generation and storage upload have completed successfully
7. IF the referenced audit ID does not exist in PostgreSQL, THEN THE WorkerManager SHALL atomically mark the job as failed and record an error indicating the audit was not found, ensuring both the status update and error recording succeed together or neither takes effect
8. IF PDF generation or storage upload fails after 3 retry attempts with exponential backoff, THEN THE WorkerManager SHALL mark the report record status as failed and retain the error reason in the job record

### Requirement 5: Job Status Monitoring

**User Story:** As a user, I want to check the progress of my background tasks so that I know when my uploads or reports are ready.

#### Acceptance Criteria

1. WHEN a user queries a job status by ID, THE QueueService SHALL return the current state (waiting, active, completed, failed, delayed), progress percentage as an integer from 0 to 100, and timestamps including createdAt, processedAt (if started), and completedAt (if finished)
2. IF a user queries a job ID that does not exist, THEN THE API SHALL return HTTP 404
3. WHILE a job is in the active state, THE WorkerManager SHALL report progress as a monotonically non-decreasing integer percentage from 0 to 100
4. WHEN a job transitions to the completed state, THE QueueService SHALL include the job result data in the status response
5. WHEN a job transitions to the failed state, THE QueueService SHALL include the failure reason and the number of attempts made in the status response
6. WHEN a job state changes in BullMQ, THE QueueService SHALL update the corresponding JobRecord in PostgreSQL within 5 seconds, mapping BullMQ states to JobRecord statuses as follows: waiting to queued, active to processing, completed to completed, failed to failed, delayed to queued; IF the database update exceeds 5 seconds, THEN THE QueueService SHALL retry the update and fail the job if the retry also exceeds the time limit

### Requirement 6: Storage Key Generation

**User Story:** As a developer, I want storage keys to follow a consistent, collision-free pattern so that files are organized and retrievable.

#### Acceptance Criteria

1. THE StorageService SHALL generate storage keys following the pattern {entityType}/{entityId}/{timestamp}-{uuid}.{ext} where entityType is one of 'audit', 'finding', 'recommendation', or 'report', timestamp is an ISO 8601 date-time string formatted as YYYYMMDD'T'HHmmss for lexicographic sorting, uuid is a version-4 UUID, and ext is the lowercase file extension
2. THE StorageService SHALL extract the file extension from the original filename and convert it to lowercase
3. IF the original filename contains no file extension, THEN THE StorageService SHALL generate the storage key without an extension segment, omitting the trailing dot
4. THE StorageService SHALL include a UUID v4 in every generated key to ensure global uniqueness
5. THE StorageService SHALL sanitize original filenames to prevent path traversal by removing forward slash (/), backslash (\), dot-dot sequences (..), and null byte characters from the filename before extracting the extension
6. THE StorageService SHALL generate storage keys that do not exceed 1024 characters in total length and contain only characters valid for S3 object keys

### Requirement 7: TLS Certificate Management

**User Story:** As a system administrator, I want all inter-service communication to be encrypted with TLS so that data in transit is protected from interception.

#### Acceptance Criteria

1. WHILE the system is running in production, THE CertificateManager SHALL establish connections to PostgreSQL, MinIO, and Redis only over TLS with `rejectUnauthorized` set to true, rejecting any connection attempt that cannot complete a TLS handshake
2. WHEN TLS certificates are configured, THE CertificateManager SHALL validate the certificate chain (CA to cert relationship) on load and apply the certificates to all subsequent connections
3. IF certificate chain validation fails on load, THEN THE CertificateManager SHALL reject the invalid certificate, log an error message indicating the validation failure reason, and retain the previously loaded valid certificate for active connections
4. WHEN a certificate file changes on disk, THE CertificateManager SHALL detect the change within 30 seconds and reload the certificate without requiring a service restart
5. IF a hot-reloaded certificate fails validation, THEN THE CertificateManager SHALL discard the invalid certificate, retain the existing valid certificate for active connections, and log an error message indicating the reload failure reason
6. WHEN the CertificateManager performs its daily expiry check and a certificate will expire within 30 days but more than 7 days, THE CertificateManager SHALL log a warning indicating the certificate identity and days until expiry
7. WHEN the CertificateManager performs its daily expiry check and a certificate will expire within 7 days, THE CertificateManager SHALL log a critical alert indicating the certificate identity and days until expiry
8. IF custom certificates are not configured, THEN THE CertificateManager SHALL fall back to the system CA store with `rejectUnauthorized` set to true

### Requirement 8: Queue Health and Worker Management

**User Story:** As a system operator, I want visibility into queue health and worker status so that I can monitor system performance and troubleshoot issues.

#### Acceptance Criteria

1. THE QueueService SHALL expose queue health metrics including connection status (boolean), waiting count, active count, completed count, failed count, delayed count, and worker count
2. WHEN the WorkerManager starts, THE WorkerManager SHALL register typed processor functions for each defined JobType ('process-file', 'generate-pdf', 'send-notification', 'cleanup-temp')
3. WHEN a SIGTERM signal is received, THE WorkerManager SHALL attempt to complete all active jobs within a configurable shutdown timeout (default: 30 seconds)
4. IF the shutdown timeout elapses while jobs are still active, THEN THE WorkerManager SHALL return remaining active jobs to the queue and SHALL NOT exit the process until the job return operation completes successfully
5. THE WorkerManager SHALL process up to a configurable number of concurrent jobs per worker (default: 3, minimum: 1, maximum: 50)

### Requirement 9: Error Recovery and Resilience

**User Story:** As a system operator, I want the system to recover gracefully from infrastructure failures so that no data is lost and service resumes automatically.

#### Acceptance Criteria

1. IF MinIO becomes unreachable (connection timeout exceeds 5 seconds), THEN THE API SHALL return HTTP 503 for storage-dependent endpoints and workers SHALL pause with exponential backoff reconnection starting at 1 second delay and doubling up to a maximum of 30 seconds
2. IF Redis becomes unreachable (connection timeout exceeds 5 seconds), THEN THE API SHALL return HTTP 503 for queue-dependent endpoints while file downloads via Presigned_URLs continue working without Redis dependency
3. WHEN Redis connectivity is restored after an outage, THE QueueService SHALL re-queue all stalled jobs for processing within 60 seconds of reconnection using BullMQ stalled job recovery, without requiring manual intervention
4. IF a file upload exceeds 120 seconds without completing, THEN THE StorageService SHALL abort the multipart upload, clean up all incomplete parts from MinIO, and update the corresponding FileRecord status to "failed"; cleanup actions (removing incomplete parts and updating FileRecord status) MAY also occur independently for other error conditions before the timeout is reached
5. WHEN a previously failed job is retried, THE WorkerManager SHALL produce identical file content at the same storage key without creating duplicate storage objects or duplicate FileRecords (idempotent processing)
6. IF MinIO or Redis experiences 5 consecutive connection failures, THEN THE API SHALL open a circuit breaker that rejects requests immediately with HTTP 503 and automatically attempts a half-open probe after 60 seconds
7. IF a worker fails during file processing after the file has been uploaded to the temp bucket, THEN THE StorageService SHALL retain the temp file and the FileRecord SHALL preserve the uploaded data until the job is retried up to 3 attempts or manually resolved

### Requirement 10: Temp File Cleanup

**User Story:** As a system operator, I want stale temporary files to be automatically cleaned up so that storage costs remain controlled.

#### Acceptance Criteria

1. THE QueueService SHALL schedule a repeatable cleanup-temp job that runs at a configurable interval (default: every 60 minutes, minimum: 5 minutes, maximum: 168 hours)
2. WHEN a cleanup-temp job runs, THE WorkerManager SHALL delete all objects in the temp bucket whose lastModified timestamp is more than 24 hours before the job start time
3. WHEN temp files are deleted during cleanup, THE WorkerManager SHALL log at info level the total number of deleted files and the total storage bytes reclaimed
4. IF the cleanup-temp job fails to delete one or more objects, THEN THE WorkerManager SHALL log the keys of the failed objects at error level, continue deleting remaining eligible objects, and retry the job according to the configured retry policy (default: 3 attempts with exponential backoff)
5. IF no objects in the temp bucket are older than 24 hours when the cleanup-temp job runs, THEN THE WorkerManager SHALL complete the job successfully without error and log at info level that zero files required cleanup

### Requirement 11: File Validation and Security

**User Story:** As a security-conscious user, I want uploaded files to be validated for type and content so that malicious files are rejected.

#### Acceptance Criteria

1. WHEN a file is uploaded, THE StorageService SHALL verify the MIME type using content inspection (magika) rather than relying solely on the file extension, and SHALL compare the detected MIME type against the allowed MIME types list for the target bucket
2. IF the content-detected MIME type does not match the declared file extension or is not in the allowed list for the target bucket, THEN THE StorageService SHALL reject the upload, prevent the file from being stored, and return an error indicating the detected type versus the expected type
3. WHEN a file is uploaded with a filename longer than 255 Unicode characters (including extension), THE StorageService SHALL reject the file and return an error indicating the filename length violation
4. THE StorageService SHALL ensure that job payloads contain only entity IDs, file references, and processing metadata, and SHALL never include user credentials, authentication tokens, or session data
5. WHEN a file operation occurs (upload, download, delete), THE API SHALL log the operation to the audit trail including the operation type, target file ID, acting user ID, timestamp, and outcome (success or failure reason)
6. IF content inspection (magika) fails or is unable to determine the file type, THEN THE StorageService SHALL reject the upload and return an error indicating that the file type could not be verified
